# RFC-SPI-PROOF-20261028：量測記錄與座標檔對應證明

狀態：已核准（2026-10-28），實作中。本規格不構成發布授權。

---

## 1. 背景（已查證的事實）

- **只存連結，不存證據。** 量測記錄與座標檔的連結只有 `records.place_id` 一個欄位（0002 schema，沒有外鍵）。
  - 上傳時，Worker 其實做了完整驗證（`cloudflare/worker.mjs:192-205`）：
    - 查座標檔是否在受控範圍內
    - 從 R2 重算座標原檔的 SHA-256
    - 重跑位號比對
  - 驗證完只留下 `unmatchedRefs`。座標指紋、料號、版次、面別與對應數都沒有保存。
- **「已綁定」只看 `placeId` 有沒有值**（`spi-spc.html:8152`）。座標檔不存在時也照樣顯示「已綁定」。
- **「驗證」只檢查單一檔案的 SHA-256**（`RecDB.get`，7840-7851 行），不檢查兩份檔案之間的對應。
- **手機卡片沒有「驗證」按鈕**（8217-8224 行）。
- **開啟舊紀錄可能偷套目前的座標檔。** `openRecord` 只對 `vendor==="lirong"` 停用座標（7969 行）。通用格式與振順豐格式在沒有 `placeId` 時，會套用使用者目前載入的 `PLACE`，跟 7963 行註解的意圖相反。
- **死碼。** `computePlacementMatch`（7749 行）用錯欄位，而且結果被 `checkMeta` 剔除；`matchRate` 的顯示（8161 行）沒有任何資料來源。
- **截圖現況（需確認 VERIFY）：**
  - 表單訊息寫「成功存入座標檔 301-**001100123**」，比表格料號少一個 1。這個訊息只是回顯輸入值（8462 行）。
  - 表格裡那筆是 301-**0011001123** v5，上傳於 10/26，狀態「已封存」，沒有「選取」按鈕。
  - 存檔後料號篩選維持原值（8467 行），剛存的檔案很可能被篩選藏起來。
  - 確認方式：把篩選改成「全部料號」。

## 2. 目標與非目標

**目標**

1. 新的受控量測上傳時，由伺服器寫入「對應證明快照」（定義見 §3）。
2. 按量測記錄的「驗證」時，伺服器重新計算並與快照比對，再用「對應證明」對話框呈現。對話框依 §6 的規則給出單一判定。
3. 舊紀錄提供「重新受控匯入」：一鍵把雲端原檔帶進受控匯入流程，產生附有證明的新紀錄。舊紀錄保持原狀。
4. 座標檔的「驗證」顯示引用它的量測記錄。
5. 防止料號打錯，並讓剛存入的資料一定看得到（§8 的 U1、U2）。

**非目標**

- 不新增表格欄位（使用者選擇把證明併入「驗證」）。既有欄位的文字、徽章與樣式可以改，範圍見 §8、§9。
- 不改寫舊紀錄的 `place_id` 或 lifecycle，也不做管理者事後綁定。
- 伺服器不做料號模糊比對，仍以精確比對為準。相近料號只在畫面上提醒。
- 不推估焊墊座標，也不新增 D1 migration。

## 3. 名詞定義

| 名詞 | 本文的精確意思 |
|---|---|
| 對應 | 一筆量測記錄的 `placeId` 指向某座標檔，且下列三項同時成立：(a) 料號相同、版次相同、量測面包含在座標面別內；(b) 兩份原檔的指紋都與入庫時相同；(c) 量測檔的位號，用該座標檔重新比對，結果與上傳時確認的相同 |
| 證明 | 由伺服器從 R2 原檔重新計算得出 (a)(b)(c) 的結果，並與上傳時的快照比對。瀏覽器另外自算量測檔指紋，作為第二道獨立檢查 |
| 受控紀錄 | `validation_source==='server_verified'` 的紀錄 |
| 舊資料 | `validation_source==='legacy'` 的紀錄（目前徽章文字是「歷史未驗證」） |
| 量測面包含在座標面別內 | 座標檔 `side==='BOTH'` 時，量測面為 TOP 或 BOT 皆可；否則兩者必須完全相同 |
| 位號 | 立榮／振順豐格式：`Component ID` 去掉 `_數字` 尾碼後的值。通用格式：位號欄的完整值 |
| 量測位號 | 至少產生一個量測點的列所含的相異位號。全空白的板，以及錯放修正後被視為未量測的板，都不計入（與 `pointKeys` 的過濾條件相同） |
| 快照 | 上傳當下寫入 `meta.placeProof` 的內容（§5.1）。之後不再改寫 |

## 4. 資料流

```
上傳：瀏覽器 ─POST /api/records─▶ Worker 既有驗證 ─▶ 寫入 meta.placeProof
驗證：瀏覽器 ─GET /api/records?link_check=<id>─▶ Worker 從 R2 讀兩份原檔，重算指紋與位號 ─▶ 回傳結果
      瀏覽器同時以既有 RecDB.get 自算量測檔指紋 ─▶ 依 §6 判定 ─▶ 對應證明對話框
重新匯入：舊紀錄 ─RecDB.get─▶ startImport（欄位可編輯、帶入舊值）─▶ 使用者選受控座標並填工單或日期
         ─RecDB.create 附 sourceLegacyId─▶ Worker 要求新原檔指紋等於舊紀錄指紋
```

## 5. 資料模型與介面

### 5.1 `meta.placeProof`（只由伺服器寫入）

```json
{ "placeId": "Xy…", "sha256": "<座標原檔 SHA-256，64 字元>", "part": "301-0011001123",
  "rev": "v5", "side": "BOTH", "unit": "mil", "measuredSide": "TOP",
  "measuredRefs": 420, "matchedRefs": 413, "coordRefsOnSide": 500, "at": 1793000000000 }
```

欄位來源：

| 欄位 | 來源 |
|---|---|
| `placeId`、`sha256`、`part`、`rev`、`side` | `coordinateScope` 回傳的座標紀錄，以及 R2 重算的指紋（`worker.mjs:192-201`） |
| `unit` | 座標紀錄的 `meta.unit` |
| `measuredSide` | 量測上傳時的 `chk.meta.side` |
| `measuredRefs` | `validateWideMeasurement`／`validateGenericMeasurement` 新增回傳的值（定義見 §3「量測位號」） |
| `matchedRefs` | `measuredRefs − missing.length`。`missing` 一定是量測位號的子集 |
| `coordRefsOnSide` | 座標項目中 `side === measuredSide` 的相異位號數 |
| `at` | 與紀錄的 `created` 相同（伺服器時間，毫秒） |

- 在 `worker.mjs` 組 `rec` 的量測分支中，`placeProof` 放在 `...chk.meta` 之後。用戶端就算送了同名欄位也會被覆蓋；`checkMeta` 本來也會剔除未知欄位。
- `lib/repo.mjs` 的 `createRecord` 白名單加入 `placeProof` 與 `sourceLegacyId`。
- 既有判定邏輯不變，只新增回傳欄位。

### 5.2 `GET /api/records?link_check=<recordId>`

- **權限**：需登入，與讀取紀錄相同，管理者與一般使用者都可呼叫。
- **路由位置**：放在既有 `?id=` 分支之前，避免被「單筆下載」攔截。

| 情況 | 狀態碼 | 回應 |
|---|---|---|
| 量測記錄有 `placeId`，座標存在 | 200 | 見下方完整結構 |
| 有 `placeId`，但座標紀錄或其 R2 原檔不存在 | 200 | `{linked:true, place:null, placeMissing:'record'│'file'}`，其餘可算的照算 |
| 沒有 `placeId` | 200 | `{linked:false, reimportedAs:[{id,created,lifecycle}]}`（依 `created` 新到舊） |
| id 不存在，或不是 `kind:'spi'` | 404 | `{error}` |
| 未登入 | 401 | — |
| 解壓或解析失敗 | 200 | 該項的 `ok:false` 並附 `error` 訊息，不回 500，讓畫面可以顯示是哪一項失敗 |

完整結構：

```json
{ "linked": true,
  "measurement": { "shaOk": true, "sha256": "…" },
  "place": { "id": "…", "part": "…", "rev": "…", "side": "BOTH", "unit": "mil",
             "lifecycle": "active│archived│legacy", "name": "X3000 V5座標檔.csv", "shaOk": true, "sha256": "…" },
  "identity": { "partOk": true, "revOk": true, "sideOk": true, "proofPlaceIdOk": true },
  "snapshot": { "present": true, "shaOk": true },
  "refs": { "measured": 420, "matched": 413, "coordOnSide": 500,
            "missing": ["…"], "wrongSide": ["…"], "unmatchedConsistent": true, "error": null } }
```

各欄位的計算方式：

| 欄位 | 計算方式 |
|---|---|
| `shaOk` | R2 原檔解壓後的 SHA-256 等於 D1 的 `sha256` |
| `snapshot.shaOk` | `placeProof.sha256` 等於座標的 D1 `sha256`，也等於 R2 重算值 |
| `identity.proofPlaceIdOk` | `placeProof.placeId` 等於紀錄的 `placeId`。沒有快照時為 `null` |
| `identity` 其他三項 | 依 §3 的定義精確比對 |
| `unmatchedConsistent` | 重算出的 `missing` 排序後，與 `meta.unmatchedRefs` 排序後完全相同 |
| `reimportedAs` | D1 查詢 `json_extract(meta,'$.sourceLegacyId') = ?` |

- 重算邏輯從上傳流程抽成共用函式 `verifyLink(repo, rec)`，上傳與 `link_check` 共用，避免兩份邏輯日後分歧。

### 5.3 重新匯入的伺服器檢查（`POST /api/records`，量測分支）

- `checkMeta` 的白名單允許 `sourceLegacyId`，格式必須符合 `ID_RE`。
- 有帶 `sourceLegacyId` 時，下列任一項不成立就回 422，並附對應錯誤碼：

| 條件 | 錯誤碼 |
|---|---|
| 該 id 的紀錄存在 | `legacy_source_missing` |
| `kind==='spi'`，且 `validation_source==='legacy'` | `legacy_source_invalid` |
| 新原檔的伺服器 SHA-256 等於舊紀錄的 `sha256` | `legacy_source_mismatch` |

- 其餘既有規則照舊：
  - 必須選擇受控座標（座標檔需為 `active`）
  - 工單或日期至少填一項
  - 有無座標位號時必須確認
  - 同一指紋重複上傳回 409
  - 同工單或同日期進入 `pending_review`
- 權限與一般量測上傳相同，登入即可。座標上傳才限管理者。

## 6. 對應證明的判定規則（由上往下，取第一個成立的）

| 判定 | 條件 | 對話框頂部橫幅 |
|---|---|---|
| ○ 無座標引用 | `linked:false` | 「這筆是舊資料，沒有座標引用，無法證明對應」＋〔重新受控匯入〕；已重新匯入過時，改顯示新紀錄的連結 |
| ✗ 無法證明 | 符合任一項：量測 `shaOk` 為 false（伺服器或瀏覽器任一方）、`place:null`、座標 `shaOk` 為 false、`identity` 任一項為 false、`snapshot.present` 為 true 但 `shaOk` 為 false、`refs.error` 有值 | 「無法證明對應：〈第一個失敗項目的原因〉」 |
| ⚠ 對應有落差 | 上面都通過，但 `unmatchedConsistent` 為 false | 「兩檔未被修改，但重新比對的無座標位號與上傳時確認的不同」，並列出差異 |
| ✓ 已證明對應 | 全部通過 | 「已證明對應：位號 413/420 對上」。沒有快照時加註「上傳時未留存快照（v10.5.0 前），以本次重算為準」 |

- 座標檔 `lifecycle==='archived'` **不會**讓判定失敗，只在第 2 列附註「座標檔已封存，不影響既有紀錄的對應」。

## 7. 畫面行為

### 7.1 對應證明對話框（量測記錄的「驗證」）

- **開啟方式**：在既有 `ver` handler（`spi-spc.html` 約 8609 行）中：
  - 保留瀏覽器端的 `RecDB.get` 檢查
  - 平行呼叫 `link_check`
  - 疊在資料庫對話框之上，`z-index` 高於 `#recPickerModal`
- **標題**：「對應證明：批號 〈lot〉」。沒有批號時改用料號。
- **頂部橫幅**：依 §6 顯示，圖示加文字，不只靠顏色。
- **內容表**（欄位：項目／量測記錄／座標檔／結果）：
  1. **原檔指紋**：顯示兩邊 SHA-256 的前 12 碼，各附〔複製〕按鈕可複製完整值；結果欄寫「瀏覽器 ✓・伺服器 ✓」。
  2. **上傳時快照**：快照指紋對照目前指紋。沒有快照時寫「未留存」。座標已封存時附註。
  3. **料號、版次、面別**：三列，兩邊數值並排。料號使用等寬字型。
  4. **位號對應**：「413 / 420 個量測位號有座標（座標此面共 500 個）」。
     - 無座標位號、跨面位號各用 `<details>` 收合，展開後最多 240px 高，可捲動。
- **按鈕**：只有〔關閉〕，在右側。
- **鍵盤與焦點**：
  - `Esc` 可關閉
  - 開啟時焦點移到標題
  - 關閉後焦點回到原本按下的「驗證」按鈕
- **讀取中**：橫幅顯示「伺服器正在重算兩份原檔…」，加上 `role="status"`。
- **錯誤處理**：
  - 401：顯示「登入已過期，請重新登入後再驗證」。
  - 網路錯誤或 5xx：顯示「驗證未完成：〈訊息〉」並提供〔重試〕。
  - 這兩種情況都不算「無法證明」。
- **結果暫存**：寫入 `REC_VER[id] = {ok, verdict}`，只在本次頁面有效，重新整理後清空。
  - 指紋欄依此顯示「原檔 ✓・對應 ✓／⚠／✗」；還沒驗證過的維持原樣。

### 7.2 座標檔的「驗證」

- 用同一種對話框外觀，包含兩段：
  - 原檔指紋
  - 「被 N 筆量測引用」：列出批號、面別、lifecycle、時間，依時間新到舊，最多 20 筆，其餘顯示「還有 N 筆」。資料來源是 `RecDB.list()` 中 `placeId` 等於此座標檔的紀錄。
- 0 筆時顯示「尚無量測引用」。

### 7.3 重新受控匯入

- **進入點**：§6 的〔重新受控匯入〕按鈕，以及 §8 U4 的欄位連結。
- **流程**：
  - `openRecord(rec, {reimport:true})` 會設定 `IMP_NEXT={reimportOf:rec}`。因為不是傳 `rec`，`recFields` 不會把欄位設成唯讀。
  - 帶入舊紀錄的批號、料號、面別、加工廠格式與鋼板厚度，全部可以修改。
  - 版次、工單、日期維持空白，由使用者填寫。
  - 匯入區上方的提示寫：「重新匯入舊紀錄 〈批號〉：請選擇受控座標並填寫工單或日期；原始檔不變，舊紀錄保留」。
- **送出**：`btnApply` 呼叫 `RecDB.create` 時附上 `sourceLegacyId`。
  - 成功：toast 顯示「已建立受控紀錄，可按『驗證』查看對應證明」。
  - 失敗：依 §5.3 的錯誤碼，在 `#recNote` 顯示可行動的說明。例如 `legacy_source_mismatch` 顯示「原始檔與舊紀錄不同，已停止」。
- **舊紀錄的顯示**：該列徽章旁加上「已重新匯入 →」連結，點擊後篩選並捲動到新紀錄。
  - 判斷來源是 `RecDB.list()` 中 `meta.sourceLegacyId` 等於本筆 id 的紀錄。

### 7.4 其他行為修正

- **開啟舊紀錄**：沒有 `placeId` 時，不論加工廠格式，一律設定 `noPlace=true`，並在 toast 說明原因。屬於行為變更，要寫進 CHANGELOG。
- **刪除死碼**：`computePlacementMatch`、`placeMatch` 的送出，以及 `matchRate` 的顯示。
- **版本**：minor 升級到 v10.5.0，同步更新 `package.json`、`package-lock.json`、`lib/version.mjs`、`#appVer` 與 `CHANGELOG.md`。

## 10. 安全、效能與相容性

- **防偽造**：`placeProof` 只由伺服器產生。`sourceLegacyId` 必須通過 SHA 相等檢查，用戶端無法把其他檔案冒充成舊紀錄的重新匯入。
- **效能**：`link_check` 的工作量等同上傳時的驗證（解壓兩檔、解析、比對）。
  - VERIFY：在 staging 用 5 萬筆級的實際檔案，量測 Worker CPU 時間是否在方案上限內。
  - 超出時的備案：改為只比對快照與指紋，位號重算移到瀏覽器。採用前需重新核准。
- **相容性**：
  - 不需要 migration。舊程式會忽略新增的 meta 欄位。
  - v10.5.0 之前的受控紀錄沒有快照，依 §6 規則仍可證明，並附註說明。
  - `idx_records_spi_fingerprint` 只約束受控紀錄，所以重新匯入同一份原檔不會跟舊紀錄衝突。
- **回退**：退回舊版時，`placeProof` 與 `sourceLegacyId` 只是不再被讀取，資料不受影響。

## 15. 實作註記（v10.5.0，與上文不同或補充之處）

- **U1 的套用範圍**：
  - 二次確認只用在座標登錄表單（`#upPlacePart`）。
  - 匯入頁上傳座標（`#placePart`）在送出前用 `confirm()` 確認。
  - 量測匯入的 `#inPart` 只做提示，因為套用前本來就要求座標料號必須與量測料號相同（`btnApply`），打錯的料號會被擋下。
  - 「相近」判定：與既有料號字面完全相同時視為既有料號；只差大小寫或空白也算相近，因為伺服器以精確比對，這類差異實際上會建立新料號。
- **U8**：沿用本專案既有的「（必填）」文字標記，不另外加紅色 `*`，避免同一程式混用兩種必填標示（06 §2）。
- **§5.2**：`refs` 多回傳 `confirmed`（上傳時確認的無座標位號）。⚠ 判定時，畫面據此列出兩邊的差異。
- **§7.4**：只設定 `noPlace` 不夠，因為通用格式的 `buildRows` 透過 `impOpts()` 直接讀目前的 `PLACE`。`impOpts()` 現在也遵守 `IMP.noPlace`。這是新測試找到的問題。
- **U12**：顯示較短的「未記錄」並設為不換行，滑鼠提示寫「舊資料未記錄板數與焊墊數」。原本的「舊資料未記錄」放在窄欄會在字中間斷行。
- **座標檔不存在時**：伺服器不回傳 `refs`，「位號對應」列顯示「沒有可比對的座標檔」。
- **視覺驗收**：用 build 產物，經實際 Worker 與記憶體 D1/R2，在本機 127.0.0.1 檢查。範圍是 1440、820、390、320 四種寬度，各跑明亮與深色主題（用 app 自己的 `data-theme`）。結果：
  - 沒有整頁溢出，也沒有內容超出面板
  - 390／320 的觸控熱區 ≥ 44px
  - 關閉後焦點回到「驗證」
  - dpr 2 下進出兩次，面板寬度不變
- **既有缺口，不在本次範圍**：明亮主題的 `.pill.ok` 文字對比是 4.39，略低於 4.5。這是全站共用 token。
- **未測（NOT TESTED）**：≥ 768px 的觸控裝置、iPhone 真機。
- **§6 判定的位置**：在瀏覽器端的 `proofVerdict()` 計算。伺服器只回傳逐項檢查結果，不回傳判定。
